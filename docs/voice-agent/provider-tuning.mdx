## What it is

The model configuration picks *which* provider and model a workflow speaks to. `service_tuning`
sets *how* that provider behaves: endpointing thresholds, voice stability, temperature, keyterms,
noise reduction. It is a key of the workflow configuration document, so it inherits from the
organization base and freezes on the run exactly like every other setting described in
[Workflow Settings](/voice-agent/workflow-settings).

```json
{
  "service_tuning": {
    "stt": {
      "deepgram": {
        "settings": { "eot_threshold": 0.8, "keyterm": ["Marbella", "parasailing"] },
        "ctor": { "mip_opt_out": true }
      }
    },
    "tts": {
      "elevenlabs": { "settings": { "stability": 0.5, "speed": 1.1 } }
    },
    "llm": {
      "_all": { "settings": { "temperature": 0.3 } },
      "openai": { "settings": { "max_tokens": 400 }, "options": { "verbosity": "high" } }
    },
    "scope": { "extraction": true }
  }
}
```

Four kinds — `stt`, `tts`, `llm` and `realtime` — each keyed by provider, and each provider takes
up to three dictionaries:

| Dictionary | Reaches | Example |
| --- | --- | --- |
| `settings` | The provider's own settings object, merged over the defaults the run already builds | `stt.deepgram.settings.eot_threshold` |
| `ctor` | Allow-listed constructor arguments, which are not settings at all | `stt.deepgram.ctor.mip_opt_out` |
| `options` | Switches that are neither, such as which OpenAI API to speak | `llm.openai.options.api` |

"Merged over the defaults" is key by key: a tuned setting replaces the value the run would have
built for that key, it does not combine with it. The one place this matters is vocabulary
biasing. The run builds the STT service with the workflow's keyword dictionary already in the
setting that carries it — `keyterm` on Deepgram (Flux and Nova) and Dograh Flux, `keyterms_prompt`
on AssemblyAI, `additional_vocab` on Speechmatics — so a tuned value for that setting **replaces**
the dictionary rather than adding to it. To keep the dictionary's words, repeat them in the tuned
list. The other biasing knobs (ElevenLabs `keyterms`, OpenAI and Sarvam `prompt`, Nova `keywords`)
never carry the dictionary, so tuning them replaces nothing.

`_all` is a provider key that applies to every provider of its kind. `llm._all.settings.temperature`
and `max_tokens` are the two fields every LLM provider declares, so they can be set once for all of
them; on a `gpt-5` reasoning model the cap is translated and the temperature is refused, see the
model-dependent table below. A provider's own key wins over `_all` key by key. The TTS section has
one `_all` key, `ctor.silence_time_s`: setting it makes every TTS service but Camb push that much
silence after each spoken turn (an aid to transports that cut the tail of a turn short). Unset,
nothing is pushed, as before.

Every knob is validated at save time against the provider's real settings. A name the provider does
not have, a value of the wrong type, a value outside a closed set, and a knob that belongs to the
other of two APIs a provider offers are each a `422` that names the path. `true` is never a value
for a numeric field: JSON booleans are rejected there rather than travelling as 1 and 0. A few
fields are narrower here than in the provider's own settings class, because the wider value would
break a call: `stt.deepgram.settings.endpointing` takes milliseconds only, `tts.openai.settings.voice`
cannot be `null`, and the Deepgram biasing knobs (`keyterm`, `keywords`, `replace`, `search`) take a
string or a list of strings, with `redact` also taking `true`, where Nova declares them as anything.

A setting whose value is an object — Cartesia `generation_config`, Gladia `pre_processing`,
`realtime_processing` and `messages_config`, Speechmatics `additional_vocab` and `known_speakers`,
Google `thinking` and `safety_settings`, Gemini Live `thinking`, `proactivity` and
`context_window_compression` — is checked against the provider's own model at save time too: a
misspelt key inside it, at any depth, and a scalar the model rejects are each a `422` naming the
path, instead of a key silently dropped or a run that fails to start.

The save cannot see which model the run will use, though, so a handful of knobs are
**model-dependent**: they are accepted and then applied only if the selected model is one that uses
them. Otherwise they are dropped when the service is built, and every drop writes one warning to
the run log naming the knob, the model and the reason:

| Knob | Applied when |
| --- | --- |
| Deepgram Flux-only settings (`eot_threshold`, `eager_eot_threshold`, `eot_timeout_ms`, `min_confidence`, `language_hints`) | The model is a Flux model |
| Deepgram Nova-only settings (`endpointing`, `utterance_end_ms`, `keywords`, `redact`, …) | The model is not a Flux model |
| `stt.deepgram.ctor.url` | The model is a Flux model. Nova takes a different constructor argument |
| `stt.deepgram.settings.language_hints` | The model is `flux-general-multi` |
| `llm.openai.options.reasoning` and `verbosity` | The model is a `gpt-5` reasoning model. On any other model, `gpt-5-chat` included, they are accepted and dropped |
| `llm.<openai>.settings.temperature` | The model is not a `gpt-5` reasoning model. Chat completions rejects temperature on those, and a knob that cannot be honoured is not dropped: the run fails to start with an error naming the model, so remove the temperature or choose another model. `gpt-5-chat` models take it |
| `llm.<openai>.settings.max_tokens` | Always, but on a `gpt-5` reasoning model it is sent as `max_completion_tokens`, the only completion cap that API accepts |

The `gpt-5` rule is keyed to the model name, not to the provider: it holds on every wire that
carries OpenAI's models over chat completions (`openai`, `atlascloud`, `openrouter` as
`openai/gpt-5…`, `azure`, `dograh`).

### Providers covered

| Kind | Providers |
| --- | --- |
| `stt` | `assemblyai`, `azure_speech`, `cartesia`, `deepgram`, `dograh`, `elevenlabs`, `gladia`, `google`, `huggingface`, `openai`, `sarvam`, `smallest`, `speaches`, `speechmatics` |
| `tts` | `azure_speech`, `camb`, `cartesia`, `deepgram`, `dograh`, `elevenlabs`, `google`, `inworld`, `lmnt`, `minimax`, `openai`, `rime`, `sarvam`, `smallest`, `speaches`, `xai`, `_all` |
| `llm` | `atlascloud`, `aws_bedrock`, `azure`, `dograh`, `google`, `google_vertex`, `groq`, `huggingface`, `minimax`, `openai`, `openrouter`, `sarvam`, `speaches`, `_all` |
| `realtime` | `azure_realtime`, `google_realtime`, `google_vertex_realtime`, `grok_realtime`, `openai_realtime`, `ultravox_realtime` |

Deepgram is one key with two wire protocols, Flux and Nova: the allow-list is the union of both,
which is why its knobs are model-dependent in the table above. OpenAI STT also has two
transcription services behind one key, but there the choice is explicit — `stt.openai.options.api`
selects it — so a knob belonging to the other one is a `422` at save time rather than a drop.

Camb exposes `user_instructions` (read on `mars-instruct` only) and the request `ctor.timeout`;
Speaches TTS speaks OpenAI's audio API and takes its `instructions` and `speed`.

## Defaults never change

Adding this section changed no default. A workflow with no `service_tuning` builds exactly the
services it built before, with the same values on the wire:

| Provider | Setting | Value |
| --- | --- | --- |
| Deepgram Flux | `eot_timeout_ms` / `eot_threshold` / `eager_eot_threshold` | 3000 / 0.7 / 0.5 |
| Deepgram Nova | `endpointing` | 100 |
| ElevenLabs TTS | `stability` / `similarity_boost` | 0.8 / 0.75 |
| OpenAI (not `gpt-5*`), AtlasCloud, Groq, OpenRouter, Google, Google Vertex, Azure, HuggingFace | `temperature` | 0.1 |
| MiniMax / Sarvam | `temperature` | 1.0 / 0.5, unless the model configuration sets one |
| Dograh, AWS Bedrock, Speaches | `temperature` | not sent at all |
| OpenAI `gpt-5*` | `reasoning_effort` / `verbosity`, no temperature | `minimal` / `low` |

Those values are asserted at the transport layer by their own control tests, and the complete set
of constructor arguments every provider receives untuned — one case per model- or
language-dependent branch, 63 in all — is compared against a capture taken from the commit before
this section, with the behaviour changes listed below as the only allowed differences. A future
change to any of them is a test failure and not a surprise on a call.

## Explicit null

A key you omit means "leave it as it is". A key set to `null` means "send this field as unset",
and the difference survives the whole cascade: an organization base can set a value and one
workflow can clear it without inventing a sentinel.

```json
{ "stt": { "dograh": { "settings": { "eager_eot_threshold": null } } } }
```

`null` is only accepted where the provider's field is genuinely nullable. On a field that is not,
it is a `422` — a service that never expected `None` there would fail mid-call instead.

Constructor arguments are not tri-state. `ctor` values go to the constructor verbatim, so an
explicit `null` there is rejected; write "use the constructor default" by leaving the key out.

## Ranges

A value outside the provider's supported range is clamped when the configuration is resolved, and
the clamp is reported as a warning rather than failing the run. The warning names the path, the
value written and the value used.

| Path | Range |
| --- | --- |
| `stt.deepgram\|dograh.settings.eot_threshold` | 0.5 – 1.0 |
| `stt.deepgram\|dograh.settings.eager_eot_threshold` | 0.3 – 0.9 |
| `stt.deepgram\|dograh.settings.eot_timeout_ms` | 500 – 60000 |
| `tts.elevenlabs.settings.speed` | 0.7 – 1.2 |
| `tts.elevenlabs.settings.stability`, `similarity_boost`, `style` | 0.0 – 1.0 |
| `llm.<provider>.settings.temperature`, `llm._all.settings.temperature` | 0.0 – 2.0 |
| `stt.elevenlabs.settings.vad_threshold` | 0.1 – 0.9 |
| `stt.elevenlabs.settings.vad_silence_threshold_secs` | 0.3 – 3.0 |
| `realtime.ultravox_realtime.settings.temperature` | 0.0 – 1.0 |
| `realtime.ultravox_realtime.settings.max_duration` (seconds) | 10 – 3600 |

`max_duration` is a number of seconds only. Ultravox would also take an ISO-8601 duration string,
but a string would skip this clamp and only fail when the run is created, so it is a `422` here.

One cross-field rule applies on top: `eager_eot_threshold` must not exceed `eot_threshold`. If it
does, it is lowered to `eot_threshold` and a warning says so.

Other numeric knobs have no declared bounds yet and are passed through as written.

## Scope

`llm` tuning applies to the conversation LLM only. A run builds other LLM instances — variable and
disposition extraction, voicemail detection, the inference LLM of a realtime pipeline — and those
keep the defaults unless you opt them in:

```json
{ "llm": { "openai": { "settings": { "temperature": 0.4 } } }, "scope": { "extraction": true } }
```

| Flag | Applies the `llm` tuning to |
| --- | --- |
| `inference` | The inference LLM of a speech-to-speech pipeline |
| `extraction` | Variable and disposition extraction |
| `voicemail` | Voicemail detection |
| `filler` | Filler-word generation. Declared, but `true` is a `422` until that role exists — see [Knobs this build does not serve](#knobs-this-build-does-not-serve) |

Extraction normally reuses the conversation LLM instead of building its own. With `llm` tuning and
`scope.extraction` left off, it can no longer share one — a shared instance would either leak the
conversation's knobs into extraction or deny extraction what it was granted — so the run builds a
separate untuned instance for it. Turning `scope.extraction` on brings sharing back.

`realtime` tuning is separate: it configures the speech-to-speech session itself, and `scope` does
not reach it.

## OpenAI options

`llm.openai.options` carries the switches that are not settings:

| Option | Values |
| --- | --- |
| `api` | `chat_completions` (default), `responses` (not in this build) |
| `reasoning.effort` | `none`, `minimal`, `low`, `medium`, `high`, `xhigh` |
| `reasoning.summary` | `auto`, `concise`, `detailed` (not in this build) |
| `verbosity` | `low`, `medium`, `high` |

`reasoning.effort` and `verbosity` are how the `gpt-5` extras above are overridden. They are
model-dependent: only a `gpt-5` reasoning model sends them, and on any other model (`gpt-5-chat`
included) they are accepted and dropped with a warning in the run log.

`stt.openai.options.api` chooses between `segments`, the segmented Audio transcription service, and
`realtime`, the realtime transcription session. Each has its own settings, and a knob belonging to
the other one is rejected rather than quietly ignored. The realtime session speaks a websocket, so
a `base_url` set on the OpenAI STT model configuration is derived into one: `https://host/v1`
becomes `wss://host/v1/realtime`. A base whose path does not end in `/v1` has no known websocket
shape and fails the run start with an error naming it; leave it unset to use OpenAI's endpoint.

## Secrets

`service_tuning.<kind>.<provider>.ctor.url` is registered as a secret: a self-hosted transcription
endpoint usually carries its credentials in the URL. It is masked when the configuration is read
back, restored from storage when a save arrives with the mask still in place, and rejected at the
organization level, where secrets do not belong. Deepgram is the provider that has it today, and it
takes effect only on a Flux model. In hosted deployments it also goes through the same egress check
as every other runtime URL, so it cannot be pointed at an internal address.

## Knobs this build does not serve

A knob this build cannot honour is a named `422`, not a value that is stored and reaches nothing.
Each is a single constant that the pull request wiring the feature flips.

| Knob | Why |
| --- | --- |
| `llm.openai.options.api: "responses"` and `options.reasoning.summary` | The Responses service still needs the node-transition deferral ported to it. |
| `stt.speechmatics.settings.turn_detection_mode` other than `external`, `stt.gladia.settings.enable_vad: true`, `stt.sarvam.settings.vad_signals: true`, `stt.assemblyai.ctor.vad_force_turn_endpoint: false` | These values hand turn detection to the provider. The pipeline always passes its own turn strategies today, and the provider's turn frames are not discarded but forwarded alongside the local ones, so one utterance would produce two turn signals. Turn handling is its own change. |
| `stt.assemblyai.settings.end_of_turn_confidence_threshold`, `min_turn_silence`, `max_turn_silence`; `stt.speechmatics.settings.end_of_utterance_silence_trigger`, `end_of_utterance_max_delay` | Any value. These tune the provider's own turn detection, and the one mode the gate above allows overwrites or ignores them. AssemblyAI's forced-endpoint mode keeps `min_turn_silence` and overwrites `max_turn_silence` on `u3-rt-pro`, and keeps `max_turn_silence` while overwriting the other two on `universal-streaming`, so no single model honours all three; Speechmatics' `external` preset switches the end-of-utterance timers off. The save cannot see the model, so the gate is model-blind by design until the turn change decides per model. |
| `scope.filler: true` | No filler LLM role is built yet, so the flag would reach nothing. It lands with the tools change; `false` and absent are accepted. |

The fields stay declared either way, so the knobs keep one name across the change.

## Knobs the provider drops

Some knobs exist on a provider's settings but never reach the wire. Those are rejected at save time
with the reason, so the setting is not stored as a placebo:

- **Dograh TTS `pitch` and `volume`** — the service copies only `speed` into the payload it sends.
- **Rime `inlineSpeedAlpha`** — neither the websocket parameters nor the message body read it.
- **Speechmatics `extra_params` and `operating_point`** — `operating_point` *is* the model for
  Speechmatics and is derived from the model configuration; `extra_params` is splatted onto the SDK
  config and would re-open it.
- **Google, Google Vertex and AWS Bedrock LLM `frequency_penalty`, `presence_penalty` and
  `seed`** — declared on their settings, but Google's generation parameters and Bedrock's
  inference config are built from temperature, `top_p`, `max_tokens` (and Google's `top_k`,
  safety settings and thinking) only. The OpenAI-compatible providers do send them.
- **Sarvam LLM `max_completion_tokens`** — the payload builder removes it; `max_tokens` is the cap
  Sarvam takes.
- **Google STT `use_separate_recognition_per_channel`** — the stream is opened with one audio
  channel and the flag is never read.
- **Ultravox `extra` keys the service or the registry owns.** `extra` is merged over the
  call-creation body last, so a key the service already set would be overwritten by it. Twelve are
  rejected: `systemPrompt`, `model`, `voice`, `temperature`, `maxDuration`, `initialOutputMedium`,
  `metadata`, `selectedTools`, `medium`, and `firstSpeakerSettings`, which the greeting decision
  rewrites on every call, plus `firstSpeaker`, its older spelling, which the rewrite does not
  cover, and `vadSettings`, which decides who ends the user turn.

Two more are accepted but conditional on a sibling setting or on the model, on top of the
model-dependent knobs listed above:

- **ElevenLabs STT VAD settings** are dropped when `ctor.commit_strategy` is `manual`, since there
  is no VAD to configure.
- **OpenAI realtime STT `prompt`** is dropped, with a warning, on `gpt-realtime-whisper`, which does
  not accept it.

Cartesia's `generation_config` is a whole object: tuning it replaces the one derived from the voice
speed and volume in the model configuration rather than merging into it.

## Behaviour changes

Seven fixes ride along with this section, because a knob cannot be exposed on a path that never
worked:

- **OpenAI TTS now uses the configured voice.** It previously ignored the model configuration's
  voice and always spoke with the OpenAI default. A stored voice that is not an OpenAI voice name
  now raises an error on the call instead of being silently replaced.
- **Cartesia `ink-2` now receives its settings object**, carrying the configured language. The
  service does not put that language on the wire today, so nothing changes on the call.
- **xAI TTS `speed` now reaches the service.** It was accepted and dropped before.
- **The segmented OpenAI STT now transcribes in the configured language.** It pinned English, so a
  Spanish call was transcribed as English. Without a configured language nothing changes.
- **`gpt-5-chat` models now take `temperature` and no longer receive `reasoning_effort` /
  `verbosity`.** They were treated as reasoning models, which they are not: they accept a
  temperature and reject the two extras. An untuned `gpt-5-chat` workflow now sends the default
  temperature and no extras.
- **Untuned `gpt-5` reasoning models on OpenRouter and Azure no longer receive the default
  `temperature`.** Those branches sent `0.1` regardless of model, which those models reject over
  chat completions. Every other model on those wires still gets `0.1`.
- **Camb TTS is built through its settings object** instead of the constructor arguments pipecat
  deprecated, which is what lets `user_instructions` reach it. The voice, model, language and
  timeout an untuned workflow ends up with are the same as before.
