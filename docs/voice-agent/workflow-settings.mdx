## Overview

Every workflow runs with a configuration document: call duration, ambient noise, turn
handling, disposition codes, text-chat timeouts and more. That document is resolved from
three layers, in order:

1. **Schema defaults** shipped with Dograh.
2. **Organization defaults** — the base every workflow in the organization inherits.
3. **The workflow definition** pinned by the run — the workflow's own values.

Later layers win key by key. A workflow only stores the keys it actually sets, so a change
to the organization base reaches every workflow that never overrode that key.

## Organization defaults

Three endpoints manage the organization base:

| Method | Path | Returns |
| --- | --- | --- |
| `GET` | `/api/v1/organizations/workflow-configuration-defaults` | The stored sparse document (secrets masked) |
| `PUT` | `/api/v1/organizations/workflow-configuration-defaults` | The document as stored |
| `GET` | `/api/v1/organizations/workflow-configuration-effective-defaults` | Schema defaults merged with the organization base, plus `warnings` |

The `PUT` stores only the keys present in the request body. A key sent as `null` at the root
of the document means "unset": it is dropped, and workflows fall back to the schema default.

Some keys are rejected with `422` at the organization level:

- **Secrets** — API keys and other credentials live on the workflow, behind their own gate.
- **External PBX** — `external_pbx_field_mappings` and `external_pbx_lead_headers` are
  guarded by the workflow save policy, which an organization layer would bypass.
- **AI model sections** — `model_overrides` and `model_configuration_v2_override` already
  have their own organization level (model configurations), so a second one would be
  ambiguous.

Custom disposition codes set in the organization base are added to the catalog returned by
`GET /api/v1/organizations/disposition-codes`, alongside the system codes and the codes
registered for the organization.

## Inherit or override

A workflow inherits every key it does not set. The workflow save stores exactly the keys the
request carries, so a sparse document keeps every other key following the organization base.
The builder still sends the full document on every save; sparse saves from the UI arrive with
the follow-up builder update.

Lists replace by default: a workflow that sets `call_dispositions` replaces the organization
catalog. To extend it instead, set the sibling flag:

```json
{
  "call_dispositions_extend_org": true,
  "call_dispositions": [{ "code": "callback_scheduled", "label": "Callback scheduled" }]
}
```

With the flag on, the workflow's options are appended to the organization catalog and
de-duplicated by `code`; an entry whose `code` already exists in the base replaces it.
The turn section has the same shape with its own flag: `turn.ignore_terms.merge_defaults`
appends the workflow's terms to the inherited list instead of replacing it.

Nested `null` values are kept as written; only a `null` at the root of the document means
"unset".

## What a run executes

The cascade is resolved **once**, when the run is created, and frozen on the run as
`effective_configurations`. Nothing re-resolves it while the call is in flight, so editing
the organization base or the workflow mid-call cannot change a run already underway.

The frozen document is visible in the run detail response:

```
GET /api/v1/workflow/{workflow_id}/runs/{run_id}
```

```json
{
  "id": 1234,
  "effective_configurations": {
    "max_call_duration": 600,
    "voicemail_detection": { "enabled": true, "api_key": "**************cdef" }
  }
}
```

Secrets are masked in that response. Runs created before this feature existed have no
frozen snapshot; they keep reading the workflow definition they pinned at creation, so their
behaviour is unchanged.

If a stored value is out of range, the resolver clamps it instead of failing the run. At run
creation the clamp is written to the API logs and is not returned to the caller; the
organization effective-defaults endpoint does return the same clamps in its `warnings` list.
Writes through the API still get a `422`.

## API clients

The external-PBX keys behave differently from every other key. While the external-PBX
integration is disabled for the organization, the workflow save no longer copies
`external_pbx_field_mappings` and `external_pbx_lead_headers` back from the stored draft, and
they cannot be set at the organization level either. A client that replaces the document
without them therefore clears them. Send both keys with their current values to keep them.
The builder does this already, so this only affects API, SDK and MCP clients.

## Backfill

Before organization defaults existed, the builder re-sent the whole materialised document on
every save, so most drafts carry every schema default as if it had been set by hand. Those
baked values would shadow the organization base forever. A one-off script strips them:

```bash
python -m scripts.backfill_workflow_configuration_defaults            # dry-run report
python -m scripts.backfill_workflow_configuration_defaults --apply    # write changes
```

It rewrites **draft** definitions only — published and archived definitions are run snapshots
and are never touched, and a workflow with no draft is left as it is. It removes only leaves
equal to the schema default; anything you set yourself, and any key the schema does not
declare, is kept. Surviving values are written back normalised, exactly as the workflow save
already stores them.
